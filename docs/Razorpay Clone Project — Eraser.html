Project Architecture Overview

A distributed, Kubernetes-native payment platform — order creation, payment authorization, bank callback simulation, settlement, webhooks — built across 7 microservices with the same architectural patterns real payment companies (Stripe, Razorpay, Adyen) use in production.

Service

Responsibility

﻿api-gateway

Auth (API key + BCrypt), rate limiting, routing

﻿payment-service

Orders, payments, state machine, bank callback simulation

﻿merchant-service

Merchant accounts, API keys, customers, webhooks

﻿operations-service

Settlements, webhook delivery, outbox relay

﻿vault-service

Card tokenization, encryption

﻿config-service

Centralized config (Spring Cloud Config, git-backed)

﻿discovery-service

Service registry

Backed by Postgres (per-service databases), Redis (rate limiting, idempotency, caching, distributed locks), Kafka (event bus), and a full observability stack (Prometheus, Grafana, Zipkin), all running as a real Kubernetes deployment (Deployments, StatefulSets, Services, ConfigMaps, Secrets).

Design Patterns Involved

Pattern

Where

What breaks without it, at scale

Idempotency keys

﻿X-Idempotency-Key header, Redis-backed IdempotencyFilter

Retries are constant at scale (timeouts, LB failover, network blips) — without this, retries create duplicate orders/charges

Distributed scheduler locking

﻿ShedLock on OutboxPoller, BankCallbackSimulator

The moment you run >1 replica of any @Scheduled job, every replica double-processes the same work

Transactional outbox

Outbox table + poller, atomic with the business write

“Write to DB” and “publish to Kafka” can’t both be guaranteed under partial failure without this — a real distributed-systems bug, not an edge case

Stateless services

Every service — DB/Redis hold all state, not memory

The actual precondition for horizontal scaling. If two consecutive requests needed the same pod, you couldn’t add replicas at all

Rate limiting

Redis-backed, per-API-key (token bucket / sliding / fixed window all implemented)

Protects the system from one bad client; without it, a single misbehaving integration takes everyone down

Circuit breaker + retry

Resilience4j around the merchant-service Feign call

More scale = more failure surface. This is what stops one slow dependency from cascading into a full outage

Full observability

Prometheus + Grafana (per-service CPU/memory), Zipkin tracing

You cannot capacity-plan — or debug — a system at scale you can’t see into

Load Testing The System

What JMeter actually is

JMeter is a Java-based load-testing tool: it opens many concurrent “virtual users” (threads), each firing HTTP requests at a target, and records latency/throughput/error rate. It has both a desktop GUI (for building a test plan) and a headless CLI mode (for running one — the GUI’s own rendering overhead becomes a bottleneck at real load, so the GUI is only ever used to edit the test, never to generate load).

1. Install JMeter

# macOS
brew install jmeter

# Confirm it's installed
jmeter --version

(Linux/Windows: download the binary from the Apache JMeter website and add its bin/ folder to your PATH.) You also need a JDK installed (JMeter is a Java application) — Java 17+ is fine.

2. Headless Mode Command

cd /path/to/full.jmx/folder
rm -rf report results.jtl          # -l results.jtl appends by default — always clear old runs first

jmeter -n -t "full.jmx" \
  -JaccessToken="<fresh JWT from a Postman login call>" \
  -JnumKeys=200 \
  -Jthreads=1000 \
  -JrampUp=30 \
  -Jduration=90 \
  -l results.jtl \
  && jmeter -g results.jtl -o report \
  && open report/index.html

Running on cloud (GKE)

Everything in this project’s k8s/ folder runs unchanged against a real Google Kubernetes Engine cluster — the whole point of Kubernetes is that the same manifests and the same kubectlcommands work regardless of what’s underneath.

1. Install the Google Cloud CLI

# macOS
brew install --cask google-cloud-sdk

# Confirm
gcloud version

2. Authenticate and pick a project

gcloud auth login                      # opens a browser to log into your Google account
gcloud projects list                   # see existing projects, or create one:
gcloud projects create my-razorpay-clone --set-as-default
gcloud config set project my-razorpay-clone

A GCP billing account must be linked to the project before you can create a cluster — gcloud billing accounts list / link via the Cloud Console if you haven’t already.

3. Enable the APIs a GKE cluster needs

gcloud services enable container.googleapis.com

4. Create the cluster

gcloud container clusters create razorpay-clone \
  --zone us-central1-a \
  --num-nodes 3 \
  --machine-type e2-standard-4       # 4 vCPU / 16GB per node — pick larger for a real 10k-TPS test

This takes a few minutes GKE is provisioning real VMs as your cluster’s nodes.

5. Point kubectl at the new cluster

gcloud container clusters get-credentials razorpay-clone --zone us-central1-a

This is the only step that “switches” where your terminal’s commands go — kubectl’s config just gained a new context pointing at GKE’s API server instead of the local kind cluster’s. Every command after this point is identical to what was run locally all session.

6. Deploy everything — same manifests, same commands

kubectl create namespace razorpay-core
kubectl apply -f k8s/stateful/     # Postgres, Redis, Kafka, Zipkin, Prometheus, Grafana
kubectl apply -f k8s/services/     # api-gateway, payment-service, merchant-service, etc.

kubectl get pods -n razorpay-core -w    # watch everything come up

Unlike local kind, a real GKE cluster costs money every hour it exists, whether or not you’re actively load-testing it — delete it (or scale node pools to zero) when you’re done for the day.

Do real companies actually spend this much?

Visa’s entire global network peaks around ~65,000 TPS — across every card, every bank, every merchant, worldwide. A single company sustaining 10,000 TPS continuously is already operating at a scale comparable to a meaningful share of a major national payment network. Real payment companies at that scale spend well into six or seven figures monthly on infrastructure — PCI-DSS compliance, multi-region failover, and 24/7 on-call all cost real money beyond raw compute.

$25-35k/month for this scale is a lean estimate, not an inflated one.

What actually got built here

  • A correct, idempotent, distributed payment flow — order → payment → async bank resolution → settlement → webhook delivery — with the exact consistency patterns (outbox, distributed locking, idempotency) that production fintech systems depend on.
  • A real Kubernetes deployment: 7 services, 3 stateful data stores, all as actual Deployment /StatefulSet /Service /ConfigMap /Secret manifests, applied, restarted, scaled, and debugged against a live cluster — the same kubectl workflow used against any cloud cluster (EKS/GKE/AKS). Moving this to a hosted cloud changes which node the API server runs on and which managed services back the stateful pieces — not whether this is “deployed.”
  • A fully wired observability stack — Prometheus scraping every service, a custom Grafana dashboard built from scratch, Zipkin distributed tracing — that was used, live, to find and confirm every bottleneck in this document, not just installed and left unused.
